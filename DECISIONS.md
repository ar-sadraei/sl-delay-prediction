# Decisions Log

This file documents the non-obvious judgment calls made during this project, and why. The goal is that anyone (including future me) can understand *why* the pipeline works the way it does, not just *what* it does.

## Project setup

**Branch per phase, PR + merge even solo.** Every phase of work happens on its own branch, gets pushed, opened as a Pull Request, reviewed, then merged into `main`. `main` stays in a working state at all times. Done even working alone, because the commit/PR history itself is part of what a project demonstrates.

**API keys are named by purpose, not by creation order.** Started with one generic `TRAFIKLAB_KEY`, but split into `TRAFIKLAB_STATIC_KEY` / `TRAFIKLAB_REALTIME_KEY` / `TRAFIKLAB_KODA_KEY` once it became clear Trafiklab treats GTFS Regional Static, GTFS Regional Realtime, and KoDa as separately-authorized APIs, each needing its own key added to the project. A generic name stops being descriptive the moment there's more than one of something.

## Data access

**KoDa dates must be based on the real current date, not an assumed one.** Hit a `400 Bad Request` ("data does not exist") when requesting a KoDa archive for a date that turned out to be in the future relative to the actual server clock. KoDa only has archives for dates that have already happened — pick historical dates deliberately, checked against `date` in the terminal, not assumed.

**`py7zr` cannot open KoDa's 7z archives; extraction uses the system `7zz` binary instead.** Confirmed the archives themselves are valid (via the `file` command and via successfully extracting other dates) but `py7zr` throws `Bad7zFile: invalid header data` even after upgrading. The actively-maintained `sevenzip` Homebrew package (binary name `7zz`, distinct from the older/unmaintained `p7zip`) handles them without issue. The pipeline shells out via `subprocess` rather than depending on `py7zr`.

**Some KoDa archives are themselves corrupted on the server side, independent of any local issue.** The archive for `2025-08-01` was only 891KB and failed to open in three independent, well-established tools (`py7zr`, `p7zip`, and current `sevenzip`) despite a fully verified, complete download (`Content-Length` matched bytes received exactly). A neighboring date (`2024-08-01`, ~59.8MB) downloaded and extracted cleanly. Lesson: if multiple independent tools agree something's broken, the input itself — not the tooling — is usually the problem. Pipeline code that processes many dates should expect occasional bad archives and handle/log failures per-date rather than assuming every date will succeed.

**SL's realtime `TripUpdates` snapshots repeat every ~15-30 seconds throughout the day; "the observed delay" for a (trip, stop) is defined as the last snapshot recorded before that stop was reached.** This is a deliberate choice, not the only valid one — an average across snapshots, or the delay at scheduled arrival time specifically, are both defensible alternatives. "Last known value" was chosen as the simplest reasonable proxy for "what actually happened."

**Historical joins must use KoDa's historical *static* GTFS snapshot for the matching date, not the live static feed.** Trafiklab's static GTFS is regenerated daily, so today's trip IDs and schedules aren't guaranteed to match what was in effect weeks or months ago. Joining old realtime data against today's schedule would silently mis-join or drop rows, more so the further back the date. KoDa serves historical static snapshots specifically to avoid this.

**GTFS scheduled times can exceed `24:00:00`** for trips that run past midnight (e.g. `25:14:00`). A plain `pd.to_datetime` call fails on this; parsing splits the time into hours/minutes/seconds and adds it as a `Timedelta` to the service date instead, which correctly rolls over into the next calendar day.

## Weather data

**SMHI parameter 1 ("Lufttemperatur — momentanvärde, 1 gång/tim") was chosen over several other same-titled temperature parameters** after checking each one's `summary` field directly against the live API rather than assuming. Parameter 1 gives one instantaneous reading per hour, which matches the trip data's hourly granularity — daily min/max/mean variants (parameters 2, 19, 20, 26, 27) would lose the hour-level detail needed for the join, and the per-minute variant (45) is finer-grained than needed.

**Station 98230 (Stockholm-Observatoriekullen A) was chosen over station 98210 (same physical location, same coordinates)** because 98230 has both current data (`latest-hour`/`latest-day`/`latest-months`) and the full quality-controlled `corrected-archive`, while 98210 only exposes the archived history — suggesting 98210 is a retired/legacy station code. Airport stations (Arlanda, Bromma) were considered and rejected in favor of a central-Stockholm station, since airports sit well outside the city center where most SL delays are actually occurring.

**SMHI's CSV export mixes real data rows with stray footnote/legend text in extra trailing columns**, and the number of metadata header rows before the real table isn't guaranteed stable. Parsing finds the real header row programmatically (by scanning for the line starting with `"Datum;"`) rather than hardcoding a `skiprows` count, and explicitly restricts to the first 4 columns (`date`, `time`, `temperature_c`, `quality`) rather than reading everything.

**The `quality` column (SMHI's G/Y flags — green = checked & approved, yellow = suspect/roughly-checked) is kept, not dropped.** No filtering decision has been made yet on whether to exclude yellow-flagged readings — deferred until Phase 3, where its effect on results (if any) can be checked directly rather than assumed upfront.

**The weather station has real gaps in its hourly record** (e.g. a missing `02:00:00` reading observed directly in the data). The join in Phase 2 needs to tolerate missing weather for a given hour (produce a null) rather than crash or silently drop the corresponding trip.

## Phase 2: Data Engineering

**Snapshots are deduplicated in a single streaming pass, not accumulated then collapsed.** An early version of the aggregation script appended every decoded row from every snapshot into one list before deduplicating — since these are `FULL_DATASET` snapshots (every file repeats every active trip), this produced ~71 million redundant rows and became impractically slow/memory-heavy. The fix: keep a dictionary keyed by `(trip_id, stop_id)`, overwriting with the newest snapshot as files are processed in order. This collapses aggregation and deduplication into one pass and keeps memory proportional to the number of unique trip-stops in a day (~535K), not the number of raw snapshot rows (~71M).

**The project was moved out of iCloud Drive entirely, onto plain local disk.** Working inside `~/Library/Mobile Documents/com~apple~CloudDocs/...` caused a `TimeoutError` when rapidly opening 6000+ small files in a loop — iCloud's sync daemon can't keep up with that I/O pattern, and files may exist only as not-yet-materialized cloud placeholders. Rather than fight this, the whole project (code + venv, rebuilt fresh) now lives under `~/Projects/`, outside any cloud-sync folder. General lesson: cloud-synced folders (iCloud, Dropbox, OneDrive, etc.) are a real, recurring risk for any project doing heavy local file I/O or containing a virtual environment — avoid for active development.

**Join keys must be checked for dtype agreement on both sides before merging, not one at a time.** `trip_id` and `stop_id` were stored as `string` in the delay data (from protobuf, always string) but as `int64` in the static GTFS CSVs (pandas auto-inferred numeric). This caused two separate merge failures, discovered sequentially rather than together. Both are now explicitly cast to `str` before any merge. General habit adopted: print the dtype of every intended join key on both sides *before* attempting a merge, rather than debugging one `ValueError` at a time.

**The delay-to-schedule join matched 534,699 of 535,514 delay records (99.85%).** The unmatched ~0.15% wasn't investigated further — most likely trips that rolled past midnight into the next GTFS service day, or minor real-world schedule/feed inconsistencies. Treated as acceptable data loss rather than a bug worth chasing, given the volume involved.

**`route_long_name` is dropped in favor of `route_short_name`.** ~90% of joined rows have a null `route_long_name` — not a data quality issue, but a genuine SL/GTFS convention: only rail-type services (metro, tram, commuter rail) are given a proper long name, while numbered bus routes (e.g. line 592) carry only a short numeric name. `route_short_name` is populated for every route and is what riders/dashboards actually reference, so it's the field used going forward.

**Large downloads use streaming with visible progress, not a single blocking call.** A 73.9MB KoDa static archive download appeared to hang using a plain `requests.get(url)` call — in reality it was working the whole time, just with zero feedback until completion, making it indistinguishable from a genuine freeze. Switched to `stream=True` with `iter_content()` and a live progress readout, which now makes a slow-but-working download visually distinguishable from an actually stuck one. Adopted as the default pattern for any future large file pull in this project.

**Secrets (`.env`) need a backup outside the local disk.** `.env` is correctly gitignored, but this means it's the *only* uncommitted thing in the project — after a project re-clone (following the iCloud move), `.env` had to be manually recreated from scratch since it was never meant to travel with git. Lesson: save real API key values somewhere durable (password manager, private note) the moment they're generated, not just in the local `.env` file.

**`weekday` is derived from the rolled-over `scheduled_dt`, not the GTFS service_date.** Trips scheduled past midnight (e.g. 27:33:44 on a Thursday service day) get a `scheduled_dt` that falls on Friday, and therefore a `weekday` value of "Friday" — even though they're part of Thursday's service day and schedule. This is the simpler default and was kept as-is, but it means very early morning trips are labeled by clock-day rather than service-day, which could matter for weekday-vs-weekend modeling around midnight boundaries.

**Row counts by `scheduled_dt` calendar date don't match per-service-day pipeline counts, due to midnight rollover.** A service day's late-night trips (past GTFS 24:00:00) land on the *next* calendar date in `scheduled_dt`. Confirmed across a 3-day pipeline run: fetching Aug 1-3 produced rows spanning Aug 1-4 in the final table, with Aug 4 holding only the small tail of Aug 3rd's after-midnight trips. This is consistent with the same rollover behavior already noted for `weekday` in Step 2.4 — grouping by `scheduled_dt.dt.date()` answers "when did this actually happen," while grouping by which KoDa archive was fetched answers "which service day's schedule was this." These are different groupings and shouldn't be conflated in later analysis.

**Fixed a real duplicate-row bug: joins now include `stop_sequence`, not just `(trip_id, stop_id)`.** The acceptance criterion "each row uniquely identified by (trip_id, stop_id, date)" failed an actual check — 2,068-2,090 duplicate rows were found. Root cause: some trips legitimately visit the same `stop_id` more than once (loop routes, out-and-back patterns), so `stop_times.txt` has two distinct rows for the same (trip_id, stop_id) with different `stop_sequence` and `arrival_time`. A single real delay observation was matching both rows in the join, producing two output rows with identical delay values. Fixed by including `stop_sequence` (already present on the protobuf's `stop_time_update`, previously unused) in both the deduplication key in `aggregate_delays` and the merge key in `join_schedule`. Confirmed: duplicate count dropped to 0, and per-date row counts increased slightly (~0.15%) as the previously-collapsed second-visit rows are now correctly counted as distinct.

**Found and fixed a silent mislabeling bug: `is_delayed` was coding "unknown" as "on time".** 659 rows (out of 1,454,188) have a null `delay_seconds`, because some protobuf `stop_time_update` entries genuinely don't carry an `arrival` field. The original `is_delayed = (delay_seconds > threshold).astype(int)` line relied on pandas' NaN-comparison behavior (`NaN > 180` evaluates to `False`), which silently coded every one of these unknown-delay rows as "on time" — a real, if small, source of incorrect labels. Fixed by explicitly preserving null in `is_delayed` when `delay_seconds` is null, rather than letting the comparison resolve it implicitly. These 659 rows should be dropped (not imputed) before model training in Phase 4, since "unknown" isn't a valid instance of either class.

## Phase 3: EDA and Statistics

**Expanded the date range specifically to test the weather hypothesis properly.** The original 3 dates (Aug 1-3, 2024) are all Stockholm summer days with zero sub-zero readings, making a genuine hot/cold comparison impossible — any split would either have an empty group or compare "slightly warm" vs "slightly warmer," not a meaningful weather contrast. Rather than force an artificial median-split on a narrow range, added winter dates (2024-01-16, 2024-02-13) specifically so the hot/cold hypothesis test has real variation to test against.

**Rescoped Phase 4 to winter-specific delay prediction, and expanded the winter sample to ~24 dates.** Initial testing with just 2 winter dates (Jan 16, Feb 13) revealed a deeper problem than an unrepresentative split: training on 3 summer dates and testing on winter data meant evaluating outside the training distribution entirely (the model never saw any example below 14°C during training). Rather than force a single model to span both regimes on 5 total dates, the project is scoped to winter delay prediction specifically — motivated directly by the Phase 3 finding that winter trips run roughly double the delay of summer trips. Expanded to ~24 winter dates (Dec 2023 - Feb 2024, excluding the Dec 21-Jan 7 holiday period, mixing weekdays/weekends) to give the model genuine within-season variation to learn from, rather than 2 isolated data points. The original 3 August dates remain in the Phase 3 EDA analysis (where the summer/winter comparison itself is the finding) but are excluded from the Phase 4 modeling table.

**Pipeline changed to per-date checkpointing to manage disk space.** Each winter date's raw KoDa archive is ~3GB uncompressed; running 24 dates simultaneously would require ~70GB+ of free space (already hit "no space left on device" with just 5 dates). build_dataset.py now saves each date's processed result as its own small parquet file (~7MB) immediately after processing, then deletes that date's raw archive/extracted files before moving to the next date — so at most one date's raw footprint exists on disk at any time. Also allows the batch to be safely interrupted and resumed, since already-processed dates are skipped on rerun.

**A second KoDa archive (2023-12-14) was corrupted server-side, consistent with the earlier 2025-08-01 case.** Failed extraction on two independent attempts with the same error, ruling out a transient issue. Left out of the winter modeling batch — 23 of the intended 24 dates were used, still within the planned 20-25 date range. This reinforces the earlier finding that occasional bad archives are a normal, expected occurrence when pulling many dates from KoDa, not something worth debugging further per-date.

**Temperature coverage is uneven across the sample: only 2 of 23 dates fall below -10°C, vs 9 dates in the -5 to 0°C band.** Any model relationship involving extreme cold rests on very few independent days and should be treated with lower confidence than the relationship in the more common mild-winter range.

**SMHI precipitation has real unreported gaps, distinct from recorded zeros.** ~57% of 2021+ hourly precipitation readings are NaN, while explicit 0.0 values also exist and are common (18,501 occurrences) — confirming NaN means "unreported" rather than an implicit zero. Left as NaN rather than filled with 0, to avoid falsely asserting "no precipitation" for hours where it's genuinely unknown (same category of bug as the earlier is_delayed NaN-mislabeling fix). is_snow_proxy/is_rain_proxy naturally exclude NaN precipitation hours from both categories (a NaN comparison evaluates False), rather than miscounting them as dry.
